## 1. 背景与问题

### 1.1 设计要求 vs 现状

业务场景文档对审批有明确要求：

| 来源 | 要求 |
|------|------|
| `07-报销申请.md` APR-001 | 单笔报销 **≤2000 元：主管审批** |
| `07-报销申请.md` APR-002 | 单笔报销 **>2000 元：总监审批 → 主管审批**（两级） |
| `07-报销申请.md` APR-003 | 超差旅标准费用：需特批流程 |
| `SECURITY.md` §4.3 | 每次调用须按「角色 + **数据归属** + 金额/范围」判定权限；查询强制注入「本人/**本部门**」条件 |

但当前数据模型**无法回答两个基本问题**：

- **谁是申请人的主管？** —— `users` 表只有 `department`（字符串）与 `role`（字符串），没有部门表与汇报线
- **谁是本部门总监？** —— 同上

因此实现退化为「取第一个管理员审批」（`api/chat.py` 中 `order_by(UserModel.created_at).limit(1)`），
与设计相差一个审批层级体系。对 200 人企业，这会导致：报销无论金额都进同一个人，审批人不是真实主管，
审批结果**不具备公司内部的授权效力**。

### 1.2 目标

1. 使系统能按「业务类型 + 金额 + 申请人部门」计算出**符合公司制度的审批链**；
2. 部门与汇报线**从上游（HR/OA）同步**，不在本系统重复维护（避免两套真相）；
3. 找不到审批人时**明确失败并转人工**，绝不猜测（错误路由比无人审批危害更大）；
4. 迁移对现有数据与接口**向后兼容**（Expand/Contract，不停机）。

## 2. 数据模型设计

### 2.1 新增：`departments`（部门树）

```python
class DepartmentModel(Base):
    __tablename__ = "departments"

    id: Mapped[str] = mapped_column(String(36), primary_key=True, default=generate_uuid)
    name: Mapped[str] = mapped_column(String(100), nullable=False)
    parent_id: Mapped[Optional[str]] = mapped_column(ForeignKey("departments.id"), index=True)
    path: Mapped[str] = mapped_column(String(500), index=True)   # 物化路径，如 /公司/技术部/后端组
    level: Mapped[int] = mapped_column(Integer, default=1)       # 层级，1=根
    manager_id: Mapped[Optional[str]] = mapped_column(ForeignKey("users.id"), index=True)
    external_id: Mapped[Optional[str]] = mapped_column(String(100), unique=True)  # 上游部门 ID，用于同步幂等
    is_active: Mapped[bool] = mapped_column(Boolean, default=True, nullable=False)
    created_at / updated_at
```

**为什么用物化路径**：200 人企业部门树通常 2~3 层，`path` 使「本部门及所有子部门」查询变为
`WHERE path LIKE '/公司/技术部%'`，无需递归 CTE，也便于缓存与调试。层级更深（>5 层）时再评估闭包表。

### 2.2 扩展：`users`

```python
# 新增
department_id: Mapped[Optional[str]] = mapped_column(ForeignKey("departments.id"), index=True)
# 保留
department: Mapped[Optional[str]] = mapped_column(String(100), index=True)   # 兼容期保留，双写
```

迁移遵循 Expand/Contract：先加列并回填（按 `department` 名称匹配），验证后再移除旧列（见 §7）。

### 2.3 新增：`approval_rules`（审批路由规则）

```python
class ApprovalRuleModel(Base):
    __tablename__ = "approval_rules"

    id: Mapped[str] = mapped_column(String(36), primary_key=True, default=generate_uuid)
    business_type: Mapped[str] = mapped_column(String(50), index=True)   # expense / seal / travel ...
    amount_min: Mapped[Optional[Decimal]] = mapped_column(Numeric(12, 2))  # 含
    amount_max: Mapped[Optional[Decimal]] = mapped_column(Numeric(12, 2))  # 不含；NULL=无上界
    step_order: Mapped[int] = mapped_column(Integer, nullable=False)       # 审批顺序，从 1 开始
    approver_type: Mapped[str] = mapped_column(String(50), nullable=False)
    approver_param: Mapped[Optional[str]] = mapped_column(String(100))     # 如 role:finance 的角色名
    required: Mapped[bool] = mapped_column(Boolean, default=True)
    enabled: Mapped[bool] = mapped_column(Boolean, default=True)
    remark: Mapped[Optional[str]] = mapped_column(String(200))
```

**`approver_type` 取值**（解析见 §4.2）：

| 取值 | 含义 |
|------|------|
| `self_dept_manager` | 申请人所在部门主管 |
| `parent_dept_manager` | 上级部门主管（总监层） |
| `top_dept_manager` | 顶层部门主管（如公司负责人） |
| `role` | 指定角色（需 `approver_param`，如 `role=finance`） |
| `user` | 指定用户（需 `approver_param=user:<uuid>`，兜底用） |

**规则示例**（对应 APR-001/002）：

| business_type | amount_min | amount_max | step_order | approver_type | approver_param |
|---|---|---|---|---|---|
| expense | 0 | 2000 | 1 | self_dept_manager | — |
| expense | 2000 | NULL | 1 | parent_dept_manager | — |
| expense | 2000 | NULL | 2 | self_dept_manager | — |

> 规则**可配置**：行政/财务可在管理后台维护（配合评审 I-3 的管理后台归属决策），
> 不在代码中硬编码「主管/总监」。

### 2.4 新增：`approval_delegations`（代理审批）

主管休假是 200 人企业的必然场景：

```python
class ApprovalDelegationModel(Base):
    __tablename__ = "approval_delegations"

    id / delegator_id (FK users) / delegate_id (FK users)
    start_at: datetime / end_at: datetime
    business_types: JSON | None   # NULL = 全部类型
    is_active: bool
    created_at
```

路由时若审批人存在**生效中的委派**，则替换为被委托人，并在审批记录中标注
（`approvals.delegated_from`），保证审计可追溯"谁实际审的、受谁委托"。

## 3. 汇报线与部门数据来源

### 3.1 原则：从上游同步，不本地重建

200 人企业的部门与汇报关系已在 HR/OA 系统维护。本系统**只做同步与缓存**，避免两套真相。

### 3.2 同步设计

| 项 | 设计 |
|----|------|
| 触发 | 定时任务（建议每日 1 次，凌晨）+ 上游 webhook（若支持） |
| 频率 | 组织变动低频；每日全量对账 + 变更增量即可满足 |
| 幂等 | 以 `departments.external_id` / `users.employee_id` 为业务主键 upsert |
| 一致性 | 同步为**全量对账**模式：本地存在但上游已删的部门 → `is_active=false`（软删，不物理删） |
| 失败降级 | 同步失败**沿用上次快照**并告警；连续失败 N 次升级告警。**绝不在同步失败时清空组织数据** |
| 审计 | 每次同步记录变更摘要（新增/停用部门数、人员调动数） |

### 3.3 同步接口约定（建议）

```
GET /internal/org/departments?since=<iso8601>   → [{external_id, name, parent_external_id, manager_employee_id}]
GET /internal/org/employees?since=<iso8601>     → [{employee_id, name, department_external_id, is_active}]
```

若上游无接口，则退化为「行政维护 CSV + 定期导入脚本」，但**仍应保留 `external_id` 字段**以便将来对接。

## 4. 审批路由算法

### 4.1 输入与输出

```
输入：business_type（expense）、amount（3000）、applicant_id（张三）、occurred_at
输出：有序审批链 [{step:1, approver_id:李总, source:parent_dept_manager},
                {step:2, approver_id:王经理, source:self_dept_manager}]
      或 失败（RoutingError，附原因）
```

### 4.2 解析流程

```
1. 规则匹配
   按 (business_type) + (amount_min ≤ amount < amount_max) 取 enabled 规则集，
   按 step_order 升序形成链；金额为空时只匹配 amount 区间为 NULL 的规则。

2. 逐级解析审批人（对每一步）
   self_dept_manager     → departments[applicant.department_id].manager_id
   parent_dept_manager   → departments[该部门.parent_id].manager_id
   top_dept_manager      → 沿 path 上溯到 level=1 的部门 manager_id
   role:<name>           → users.role = <name> 且 is_active 的成员（见 4.3）
   user:<uuid>           → 直接指定

3. 逐级校验
   a) 审批人不得为申请人本人 → 若是，自动上溯一级（self→parent→top）；
      仍冲突则失败（避免自审）
   b) 审批人必须 is_active 且未离职 → 否则上溯或失败
   c) 同一链中审批人不得重复 → 去重后若只剩 1 步且该步为 required，仍可用；
      若去重导致 required 步骤消失 → 失败并告警（规则配置有问题）

4. 委派替换
   若审批人存在生效中的委派（§2.4），替换为被委托人，记录 delegated_from。

5. 失败处理
   任一步无法解析出审批人 → RoutingError，不生成审批链；
   调用方（chat/confirm）转为「待人工指派」状态并通知行政专员（见 §4.4）。
```

### 4.3 角色类审批人的多成员处理

`role:finance` 可能对应多人。建议策略：

- **默认**：全部加入该步骤（任一人审批通过即该步完成，先到先得），
  其他待办自动关闭——这与多数企业的"财务复核岗"实际操作一致；
- **可选**：配置为会签（全部通过才算该步完成），适用于需要双人复核的用印/合同场景；
- 实现上通过 `approval_rules.remark` 或独立配置位区分，**首期用默认策略即可**。

### 4.4 兜底与用户可见行为

| 情况 | 用户可见行为 | 系统动作 |
|------|--------------|----------|
| 规则中无匹配项（如新业务类型未配置） | 「已提交，等待人工指派审批人」 | 任务置 `processing`，通知行政专员 |
| 审批人无法解析（部门无主管） | 同上 | 同上 + 告警（组织数据可能不完整） |
| 审批人离职/停用 | 同上 | 自动上溯一级；仍失败则人工指派 |
| 规则配置冲突（去重后 required 步骤消失） | 「已提交，等待人工指派」 | 告警至管理员（配置错误需修复） |

**原则**：宁可转人工，也不猜测审批人——错误路由会让审批失去效力。

## 5. 数据归属与查询权限（配合 SECURITY §4.3）

`SECURITY.md` 要求「查询类操作强制注入数据归属条件，禁止先查全量再过滤」。落地方式：

| 角色 | 可见范围 | 注入条件 |
|------|----------|----------|
| `employee` | 本人 | `WHERE user_id = :me` |
| `approver`（有下属） | 本人 + 直接下属 | `WHERE user_id = :me OR user_id IN (直接下属)` |
| 部门主管 | 本部门及子部门 | `WHERE user_id IN (SELECT id FROM users WHERE department_id IN (本部门子树))` |
| `finance` / `hr` | 按业务类型的全量（受审计） | 不注入归属，但**每次访问记审计** |
| `admin` | 全量（受审计） | 同上 |

「本部门子树」查询：`departments.path LIKE :dept_path || '%'`（利用 §2.1 的物化路径）。

> 现状差距：当前 `/tasks/my` 仅按 `user_id` 过滤，`/tasks/pending-approval` 按审批记录过滤（已正确）；
> **部门维度的可见性尚未实现**，随本设计补齐。

## 6. 缓存策略

沿用 `部署与运维.md` §8.3 的缓存原则（TTL ≤5 分钟、变更广播清理）：

| 对象 | Key | TTL | 失效 |
|------|-----|-----|------|
|  departmental 树 | `org:tree` | 10 分钟 | 同步任务完成后主动清理 |
| 用户部门与角色 | `rbac:{user_id}` | 5 分钟 | 人员调动时清理 |
| 审批路由结果 | 不缓存 | — | 金额/规则/组织任一变化都会影响结果 |

## 7. 迁移方案（Expand / Contract）

遵守 `部署与运维.md` §5.4 的不停机迁移原则：

| 阶段 | 动作 | 回滚 |
|------|------|------|
| **Expand** | 新增 `departments` / `approval_rules` / `approval_delegations` 三表；`users` 加 `department_id`（可空）；`approvals` 加 `delegated_from`（可空） | 删除新表/新列，旧代码不受影响 |
| **Backfill** | 从 `users.department` 名称匹配生成部门树（无匹配则挂根节点并标记待人工整理）；导入默认审批规则（按 APR-001/002） | 清空新表重来 |
| **双读校验** | 路由时同时计算「新算法结果」与「旧逻辑结果」，仅记录差异（不改变实际行为），观察 1~2 周 | 关闭校验开关 |
| **Cutover** | `chat.py` 改为调用新路由；`users.department` 停止写入 | 回滚代码即可（新表不影响旧逻辑） |
| **Contract** | 确认无引用后移除 `users.department` 列与旧逻辑 | — |

## 9. 测试要点

| # | 用例 | 断言 |
|---|------|------|
| T-1 | 报销 1500 元（≤2000） | 审批链 = [主管] 单级 |

| T-4 | 部门无主管 | `RoutingError` + 任务转人工指派 + 告警 |

| T-7 | 规则未配置的新业务类型 | 转人工指派，不抛未捕获异常 |
| T-8 | 组织同步失败 | 沿用旧快照 + 告警；组织数据未被清空 |
| T-9 | 上游删除部门 | 本地软删（`is_active=false`），历史审批记录仍可追溯 |

### 与本设计的偏离（需在验收时知悉）

1. 迁移回填**不设置部门主管**（旧数据只有部门名，无汇报线）：因此既有环境的部门需由 HR 同步或人工补齐主管，
   在此之前相关单据走「待人工指派」，这是设计 §4.4 的预期行为而非缺陷。
2. 新增 `approvals.approver_source` 与 `approvals.mode` 两列（设计未列）：前者用于审计「为何是这个人审批」，
   后者让在途审批不受规则事后修改影响。
3. `users.department`（旧字符串列）在本次迁移中保留并双写，Contract 阶段（移除旧列）另排。
4. **规则匹配维度只有「业务类型 + 金额」**：场景文档里按槽位分支的审批要求（用印的印章类型、
   请假的连续天数、资产的单项价值、物资的单价）用本设计的 `approval_rules` 表达不了，
   需要扩展匹配维度（如增加条件表达式或 `slot_key/slot_value` 列）——见下节。
5. **审批链只在 `expense` / `seal` 两类业务上生效**：是否发起审批由 `HIGH_RISK_BUSINESS` 决定，
   其余要求审批的场景（请假/物资/差旅/资产）仍走「提交即完成」。这是覆盖面差距，不是路由缺陷。
