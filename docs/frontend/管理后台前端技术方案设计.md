## 1. 文档目的与本方案的边界

本方案回答评审报告 **I-3「管理后台的设计与前端方案矛盾」**：PRD §5.6 要求系统管理模块，
而《前端技术方案设计》把「管理后台」标为 P2 待下个迭代。本方案给出首期可交付的管理后台
前端设计，并明确它与员工端 H5 的边界。

**本方案覆盖**：需要新建的独立前端工程 `frontend-admin/`（技术选型、工程结构、路由、
四个模块的界面与交互、API 层、登录、错误处理、测试、部署），以及为支撑它而必须补的
**后端增量改动**（见 §10）。

**本方案不覆盖**：后端业务逻辑改造、权限模型设计、员工端 H5 的任何改动。

## 3. 待决事项

以下三项**不由本方案单方面拍板**，开工前需确认；已给出推荐值与影响面，
其中第 3 项不阻塞开发。

### 3.1 I-3 的正式结论需要产品/行政签字

本方案的技术设计已按「首期交付 UI」展开，但**上线归属**本身是业务决策：
一旦交付，行政专员将改为在界面上维护审批规则与组织数据，而不再依赖开发跑脚本。
需确认的事项：

- 首期是否确实交付 UI（若否，本方案延后，继续用 `scripts/manage_approval_rules.py` 过渡）
- 谁负责日常维护（建议指定至少 2 人互为备份，与知识库责任人同一思路，见需求文档 §5.6）
- 管理后台的**访问范围**是否限于内网（决定 §13 是否加 nginx IP 白名单）

**影响面**：若结论是「首期不做 UI」，本方案整体挂起，§10 的后端改动中仅第 1 项
（审计查询留痕，合规要求）仍应单独落地。

### 3.2 后端改动第 5 项（用户清单端点）是否纳入首期

`GET /admin/users`（含 `role`，支持按部门/角色/关键字过滤）用于核对 HR/法务人员的
`role` 打标——这是交接文档列为「生产启用审批链前置」的非代码事项之一，当前只能查库核对。

- **纳入**（推荐）：把投产阻塞项变成界面上可做的事，约 25 行 + 用例，只读查询、零迁移
- **不纳入**：首期组织页只能核到部门与主管层级，`role` 打标核对仍靠数据库查询；
  该能力顺延到二期

### 3.3 部署形态

推荐**同域子路径 `/admin/`**（复用现有证书与 CORS 配置，运维成本最低），本方案按此展开。
若改为独立子域，仅需调整 `vite.config.ts` 的 `base` 与 nginx 配置，**不影响本方案的其余设计**，
故不阻塞开发。

## 4. 定位与边界

### 4.1 目标用户与使用场景

| 角色 | 关注的功能 | 使用场景 |
|------|-----------|----------|
| 行政专员 | 审批规则配置、组织架构查看 | 制度/流程调整后维护规则；生产启用审批链前核对组织数据完整性 |
| HR | 组织架构查看 | 核对部门与主管、核对 HR/法务人员的角色打标 |
| 系统管理员 | 审计日志、仪表盘 | 合规审计、排障、运营度量 |

场景特征：**PC 桌面浏览器、办公时段、低频少量操作**。这与员工端 H5 的场景
（手机、高频、单次办一件事）根本不同——这是拆成独立应用的主要理由（决策 A-1）。

### 4.2 与员工端 H5 的边界

| 维度 | 员工端 H5 | 管理后台 |
|------|-----------|----------|
| 入口 | 飞书 H5（工作台/聊天内打开） | PC 浏览器，同域 `/admin/` |
| 用户 | 全体员工 | 仅 `role == "admin"` |
| 鉴权 | 飞书 OAuth（H5 容器内） | 飞书 OAuth（浏览器跳转），**独立回调地址** |
| 工程 | `frontend/` | `frontend-admin/`（独立构建与部署） |
| 主题 | 飞书主题包 + H5 专项依赖 | Semi Design 默认主题，不含 H5 依赖 |
| 设备适配 | 移动优先 | 桌面优先，**不做移动端适配** |

两者共用同一后端与同一套 `/admin/*` 接口，不存在两套数据源。

### 4.3 非目标（首期明确不做）

写在这里以避免预期错位——这些项目**不是被遗漏，是有意后置**：

| 非目标 | 原因 |
|--------|------|
| 权限配置模块 | 后端**没有任何**维护 `users.role` / `users.permissions` 的接口，需先定权限模型 |
| 知识库管理 | 后端 `/knowledge/*` 缺「编辑」接口（PRD §5.6 要求上传、编辑、删除） |
| 工具配置 | `PUT /admin/tools/{id}/config` 是空实现（仅回显，无持久化） |
| 部门/主管/角色的编辑 | 组织数据以 HR 为权威源，本地改会被下次同步覆盖；且后端无端点 |
| 审计导出 | SECURITY §6.4 要求「导出需审批」，需先做审批流 |
| 代理审批委派管理 | 后端 `GET/POST /admin/approval-delegations` 已就绪，但使用频次低，二期随审批工作台一起做 |
| 移动端适配 | 管理后台面向 PC 办公场景 |
| 乐观更新 | 审批规则改动直接影响单据路由，必须等服务端确认（见 §11） |

### 4.4 与脚本的分工

首期交付 UI **不废弃脚本**，两者共用同一套后端接口，不存在两套真相：

| 场景 | 用哪个 |
|------|--------|
| 日常单条规则维护、查看组织数据、查审计 | 管理后台界面 |
| 定时组织同步（建议每日凌晨） | `scripts/sync_org.py`（定时任务） |
| 规则批量导入/导出、CI 场景 | `scripts/manage_approval_rules.py` |

## 5. 技术选型与工程结构

### 5.1 核心依赖

版本以现有 `frontend/package.json` 实际使用为准（决策 A-4：同构自建，减少新变量）：

| 层级 | 选型 | 版本 | 理由 |
|------|------|------|------|
| 框架 | React | 19.2+ | 与员工端一致 |
| 语言 | TypeScript | 6.0+ | 与员工端一致 |
| 构建 | Vite | 8.x | 与员工端一致 |
| UI 库 | Semi Design | 2.103+ | **本身就是中后台组件库**（Table/Form/Tree/Descriptions 齐全），无需再引 Ant Design |
| 主题 | Semi 默认主题 | — | 不用飞书主题包（那是 H5 视觉语言） |
| 状态管理 | Zustand | 5.x | 仅 auth 一个 store（四个模块之间无共享状态） |
| HTTP | Axios | 1.20+ | 拦截器解信封、注入 JWT |
| 路由 | React Router | 7.x | 与员工端一致 |
| 代码检查 | oxlint | — | 与员工端 `lint` 脚本一致 |

**刻意不引的依赖**：

- 飞书 H5 专项依赖（飞书 JSAPI、vconsole）——管理后台不在飞书容器内运行
- `@tanstack/react-query`——员工端装了未使用（已列入死代码清单），本方案用自写的
  `useRequest` hook 满足四个模块的取数需求，不引框架抽象
- 图表库（ECharts/Recharts）——首期图表只有「热门意图 Top5」一处，用 Semi Progress 或
  纯 CSS 条形即可；《项目完善与上线指南》里的 ECharts 选型可顺延到真有大屏需求时

### 5.2 工程结构

按 **feature 分层**（而非「页面/组件/api」分层）：四个模块之间几乎没有共享状态，
每个模块自带 api 与类型最好读；真正的通用件（表格、条件编辑器）沉到 `components/`。

```text
frontend-admin/
├── src/
│   ├── main.tsx                    # 挂载
│   ├── App.tsx                     # 路由表 + 管理员门禁
│   ├── api/
│   │   ├── client.ts               # axios 实例：注入 JWT、解信封、401/403 处理
│   │   ├── auth.ts                 # login-url、callback、me、dev-login、logout
│   │   └── admin.ts                # dashboard/metrics/approval-rules/departments/audit-logs/users
│   ├── components/
│   │   ├── DataTable.tsx           # 统一列表：加载态、空态、分页、错误重试
│   │   ├── PageHeader.tsx
│   │   ├── ConditionEditor.tsx     # 审批规则条件构建器（见 §7.2）
│   │   └── JsonViewer.tsx          # 只读 JSON 展示（审计原文、条件预览）
│   ├── features/
│   │   ├── auth/                   # LoginPage、CallbackPage、authStore、RequireAdmin
│   │   ├── dashboard/              # 指标卡、热门意图
│   │   ├── approval-rules/         # 列表、RuleFormDrawer、ruleFormat.ts（纯函数）
│   │   ├── org/                    # 部门树、主管缺失告警、同步
│   │   └── audit-logs/             # 筛选、列表、原文展开
│   ├── layout/                     # AppLayout：侧边导航 + 顶栏
│   ├── hooks/useRequest.ts         # data/loading/error/refresh
│   └── types/admin.ts              # /admin/* 响应类型
├── vite.config.ts                  # dev 端口 3001，/api 代理到 8000
└── package.json
```

**开发端口 3001**（员工端占用 3000，后端 8000，互不冲突）。

## 6. 信息架构与路由

| 路径 | 页面 | 门禁 | 说明 |
|------|------|------|------|
| `/login` | 登录页 | 公开 | 「飞书授权登录」按钮 + 失败原因回显 + 开发登录区块（仅 DEV 构建） |
| `/auth/callback` | OAuth 回调 | 公开 | 收 `code`/`state` → 换 JWT → 校验管理员 → 跳首页 |
| `/` | 仪表盘 | 管理员 | 今日指标 + 累计运营指标 + 热门意图 |
| `/approval-rules` | 审批规则配置 | 管理员 | 列表 + 新建/编辑抽屉 + 删除确认 |
| `/org` | 组织架构 | 管理员 | 主管缺失告警 + 部门树 + 详情 + 手动同步 |
| `/audit-logs` | 审计日志 | 管理员 | 筛选 + 分页 + 原文展开 |
| `*` | — | — | 重定向到 `/` |

**布局**：左侧固定侧边导航（四项，带图标），顶栏显示当前管理员姓名/工号与「退出」。

**权限只做一层**：后端 `/admin/*` 是严格的 `role == "admin"`，因此前端只做
「非 admin 直接拒绝进入」这一层门禁，**不设计细粒度权限**。理由：后端没有更细的授权模型，
前端假装分级只会制造「界面上藏了按钮就等于安全」的错觉。细粒度权限等二期权限配置模块
连同后端模型一起设计。

## 7. 模块设计

### 7.1 仪表盘

**数据来源**：`GET /admin/dashboard`、`GET /admin/metrics`。

**布局**：顶部四张指标卡，下方左右两块（热门意图 Top5、运营指标）。

**两处必须处理的展示陷阱：**

**(1) 口径必须分别标注。** 后端 `today_conversations` / `today_tasks` 是**今日**口径
（`created_at >= 今日 0 点`），而 `transfer_rate` / `completion_rate` 是**全量**口径
（分子分母都是全量计数）。混在同一排卡片里会被读成「今日转人工率」，
故卡片上分别标注「今日」与「累计至今」。

| 卡片 | 字段 | 口径 |
|------|------|------|
| 今日对话数 | `today_conversations` | 今日 |
| 今日任务数 | `today_tasks` | 今日 |
| 转人工率 | `transfer_rate` | **累计至今** |
| 任务完成率 | `completion_rate`（来自 `/admin/metrics`） | **累计至今** |

**(2) 未接入的指标不显示 0。** `metrics` 的 `llm_calls`、`token_cost`、
`avg_response_time` 当前恒为 `0`（后端代码留有 TODO，缺 LLM 调用埋点）。
这三个指标显示为**「未接入」并附原因说明**，不显示 `0`——显示 0 会让管理员判断成
「系统从未被调用」，是误导。

**热门意图**：`top_intents` 的 `intent` 是英文标识（`leave_request` 等），
前端维护一张中文映射表；映射不到时**原样显示英文**（不猜测含义）。

### 7.2 审批规则配置（首期工作量最大）

**数据来源**：`GET /admin/approval-rules?business_type=`、`POST /admin/approval-rules`
（带 `id` 即更新）、`DELETE /admin/approval-rules/{rule_id}`。

#### 7.2.1 列表

列：业务类型、金额区间、步骤、审批人、审批模式、条件、状态、备注、操作。
支持按 `business_type` 筛选（后端参数已支持）。

两个展示细节必须做对：

- **金额区间**：语义是「**含 `amount_min`、不含 `amount_max`**」，为空表示无界。
  展示为 `0 ~ 2000`、`2000 ~ 不限`，空值显示「不限」而**不是 0**——
  显示 0 会被理解成「金额必须为 0」。
- **条件列**：把 `[{"slot","op","value"}]` 渲染成可读摘要（如「天数 > 2」
  「印章类型 属于 [合同章, 法人章]」）；条件为空时显示**「无条件（兜底）」并加视觉标记**。
  这是最容易看漏的一列，而它的含义（兜底规则）恰恰是最容易配错的（见 §7.2.3）。

#### 7.2.2 表单字段（与后端校验一一对应）

| 字段 | 控件 | 约束（与后端一致） |
|------|------|-------------------|
| `business_type` | 下拉（可搜索 + 允许自由输入） | 必填。选项来源见下方说明 |
| `amount_min` / `amount_max` | 数字输入 | 可空=无界；两者都有时 `min < max` |
| `step_order` | 数字输入 | ≥ 1，从 1 开始 |
| `approver_type` | 下拉 5 选 1 | `self_dept_manager` / `parent_dept_manager` / `top_dept_manager` / `role` / `user` |
| `approver_param` | 文本输入 | `role` 或 `user` 时**必填**；`role` 需与用户的 `role` 打标一致（如 `hr`、`legal`） |
| `approval_mode` | 单选 | `any_one`（任一人通过）/ `all_must`（会签） |
| `required` | 开关 | 该步骤是否**必需**，见下方说明 |
| `enabled` | 开关 | 默认开；停用的规则不参与匹配 |
| `condition` | 条件构建器 | 见 §7.2.3 |
| `remark` | 文本域 | 可空 |

**`business_type` 的选项来源**：`APPROVAL_REQUIRED_BUSINESS_TYPES` 配置项里的业务类型，
加上现有规则中已出现过的业务类型（去重）。后端对 `business_type` 不做取值校验，
故**允许自由输入**以支持新增业务——写死下拉会挡住新业务接入。

**`required` 的语义（必须在界面上说明）**：标记该步骤为必需。路由算法在链内按审批人去重后
会统计「必需的步骤组」是否仍然存在；**若必需步骤全部因去重而消失，路由判定为失败**
（按「规则配置有问题」处理）：任务转人工指派并告警管理员。因此该字段的界面文案为：

> 必需步骤：勾选后该步骤不可因链内去重而消失；若去重后必需步骤全部消失，
> 单据会转人工指派并告警管理员。

**`enabled` 与删除的关系**：停用（`enabled=false`）用于**临时**让规则不参与匹配且保留配置；
删除是永久移除。界面上应引导优先用停用（尤其是排查路由问题时）。

前端**镜像后端的全部校验**（上述约束）并给出同样的中文原因，命中即本地拦下，
避免一次无谓往返；但后端仍是权威，其返回的 `message` 原样展示。

#### 7.2.3 条件构建器（本页核心）

后端条件语义（读自 `core/approval/conditions.py`）：

- 结构：`[{"slot": "days", "op": "gt", "value": 2}, ...]`
- 多条件之间是**隐式 AND**（`evaluate_conditions` 逐个求值，全部通过才成立）
- 算子集合固定 8 个：`eq` `ne` `gt` `gte` `lt` `lte` `in` `not_in`
- `in` / `not_in` 的 `value` **必须是数组**，其余算子为单值
- **槽位缺失即条件不成立**（不猜测）
- `days` 是**派生字段**：由 `start_date`/`end_date` 算出，含首尾

界面设计（要点是**如实呈现后端语义，不美化**）：

- 行式布局：`槽位 | 算子 | 值` + 增删行
- 行间关系**只能显示为「且」**。后端是隐式 AND，界面上给「或」的选项就是在撒谎——
  需要「或」的场景应拆成多条规则
- 算子下拉只放上述 8 个，不给自由表达式输入（后端不做表达式解析）
- 选择 `in` / `not_in` 时，值输入切换为**多值标签输入**（对应后端的数组要求）；
  其余算子保持单值
- 槽位给常用候选：`amount`、`days`、`seal_type`、`leave_type`、`expense_type`；
  其中 `days` 标注「由起止日期派生，含首尾」——不知道它是派生字段的人会以为要自己写入。
  同时**允许自由输入**（槽位随业务类型可变，写死候选会漏）
- 提供「查看 JSON」只读抽屉供排障，但**不做 JSON 直接编辑**——自由编辑会绕过校验

#### 7.2.4 兜底规则的内联警告

当 `amount_min`、`amount_max`、`condition` **都为空**时，表单内联高亮提示：

> 这是**兜底规则**：本步骤内未被其他条件/金额区间命中的请求都会落到它上面。
> 同一步骤内，兜底规则让位于条件/区间规则（避免分支被稀释成多人并行）。

不写这条，管理员很容易把兜底规则当成「一条普通规则」，从而配出「所有人并行审批」的链路。

#### 7.2.5 删除与页面说明

- **删除**：二次确认，文案写明「**在途审批不受影响**——步骤模式（任一人/会签）在生成
  审批链时已快照到 `approvals.mode`」
- **页面顶部常驻说明条**：

> 本页决定**审批链怎么走**。某个业务**是否需要审批**由后端配置
> `APPROVAL_REQUIRED_BUSINESS_TYPES` 决定，与本页无关；该业务一条规则都没配时，
> 单据会转人工指派（并通知行政专员），而不是自动通过。

不写这条，管理员会误以为「配了规则才走审批」，从而在缺少规则时误判单据会直接通过。

### 7.3 组织架构

**数据来源**：`GET /admin/departments`（返回**扁平列表**，带 `parent_id`/`path`/`level`，
由前端组树）、`POST /admin/org/sync`。

**布局**：置顶「主管缺失」告警区 + 左侧部门树 + 右侧选中部门详情。

**主管缺失告警区（本页存在的主要理由）**：迁移按设计**不回填主管**（组织数据不完整时
宁可走人工指派，也不猜审批人），而主管缺失会导致该部门下所有单据无法自动路由。
故列出所有 `is_active` 且 `manager == null` 的部门，并写明补齐路径：

> 这些部门下的单据无法自动路由审批人，会转人工指派。补齐方式：**在 HR 系统维护负责人后
> 同步**（本地不直接修改——组织数据以 HR 为权威源，本地改会被下次同步覆盖）。

**部门详情**：名称、路径（`path`）、层级、上游 `external_id`、主管（姓名 + 工号）、启用状态。

**手动同步**：按钮 + 二次确认，确认框文案写明「组织数据以 HR 为权威源，同步失败会沿用
上次快照、不会清空组织数据」；结果**如实回显**后端返回的 `ok` 与原因，失败不提示成功。

**这页是只读的**：不提供「设置主管」「改部门」。理由见 §4.3。

**能力边界**：核对 HR/法务人员的 `role` 打标需要用户清单，而 `/admin/*` 下**没有用户
列表端点**。首期组织页因此只能核到部门与主管层级；`role` 打标核对依赖 §10 第 5 项
（可选后端改动）是否纳入首期。

### 7.4 审计日志

**数据来源**：`GET /admin/audit-logs`（支持 `user_id`、`action` 模糊、`page`、
`page_size` ≤ 100）。

**筛选**：工号/用户 ID、`action`（模糊）、日期区间。

> 日期区间依赖 §10 第 2 项（后端加 `start`/`end` 参数）。**不能在前端过滤**——
> 前端只能过滤当前页，会给出「筛选后只有 3 条」这类错误结论。

**列表列**：时间、操作者、`action`、`resource_type` / `resource_id`、`decision`、IP。

- 操作者显示姓名 + 工号，依赖 §10 第 3 项（后端补 `user_name`）；未纳入时显示 `user_id`

**原文展开（按决策 A-3 与 SECURITY §6.4）**：

- **默认折叠**，行展开后以只读 JSON 展示 `input_data`，支持一键复制
- 展开区固定显示两条提示：
  - 「本次查看**已记入审计**」（对应 §6.4 的「查询行为本身留痕」，让管理员知情）
  - 「含个人数据（如员工对话原文），仅用于审计排查」
- 默认折叠是有意设计：**不把员工对话原文直接铺在列表里**

**分页**：`page` / `page_size`（后端上限 100）。

**空态区分两种情况**：「没有匹配当前筛选的记录」与「系统还没有审计数据」——
前者提示放宽筛选，后者提示系统可能刚部署。这两者的下一步动作完全不同。

## 8. 数据流与 API 层

### 8.1 `api/client.ts`

- `baseURL` 取 `import.meta.env.VITE_API_BASE_URL`（默认 `/api/v1`）
- 请求拦截器：从 localStorage 读 token，注入 `Authorization: Bearer <token>`
- 响应拦截器：解 `{code, message, data}` 信封
  - `code === 0` → 返回 `data`（业务代码直接拿数据，不重复解包）
  - `code !== 0` → 抛出携带后端 `message` 的业务错误
  - HTTP 401 / token 过期 → 清 token，跳 `/login?reason=expired`
  - HTTP 403 或 `code === 40003` → **不静默跳转**，提示「无管理员权限」并显示当前账号
    工号。否则用户分不清是权限问题还是登录过期

### 8.2 类型定义

`src/types/admin.ts` 为五类响应定义 TS 类型，字段与后端序列化函数
（`_rule_to_dict`、部门列表、审计日志列表、dashboard、metrics）**逐字段对应**，
避免前端自行发明字段名。

### 8.3 取数方式

自写最小 `useRequest` hook（`data` / `loading` / `error` / `refresh`），
列表分页与筛选由参数驱动。**不引 `@tanstack/react-query`**：四个模块之间无缓存共享需求，
引框架抽象属过度设计。

## 9. 登录与鉴权

### 9.1 生产流程

复用现有飞书 OAuth 授权码流程（与员工端同一后端接口），但**回调地址不同**：

1. 未登录访问任意路由 → 重定向 `/login`
2. 点「飞书授权登录」→ `GET /auth/feishu/login-url` → 跳转返回的 `login_url`
3. 飞书授权后回调到**管理后台自己的** `/auth/callback?code=<code>&state=<state>`
4. 前端以 `code`/`state` 请求后端 `GET /auth/feishu/callback` 换取 JWT
5. 存入 localStorage 后调用 `GET /auth/me`，**校验 `role === "admin"`**
6. 通过则进入 `/`；不是管理员则**清除 token 并明确提示「当前账号无管理权限」**，
   而不是放进主界面让它到处 403

### 9.2 开发环境登录（与员工端的刻意差异）

员工端 `redirectToLogin()` 在 DEV 构建下**写死用 `admin001` 登录**，一次点击即成为管理员。
**管理后台不照抄这个做法**，理由两条：

1. 它会掩盖权限校验——永远测不到「非管理员被拒」这条路径
2. 一旦构建环境判断出现偏差（预览/预发构建保留了该分支），就成了直达管理员的登录后门

因此管理后台的做法是：

- 登录页上一个**独立的「开发登录」区块**，需**手动输入工号**（不预填 `admin001`）
- 区块旁标注「**仅本地开发可用，生产构建不包含此分支**」
- 以 `import.meta.env.DEV` 守卫
- **把「生产构建产物中不出现该区块」列为上线检查项**（见 §13.3）

### 9.3 回调地址的部署前置

后端 `FEISHU_REDIRECT_URI` 是**单值配置**，而管理后台的回调路径与员工端不同
（且可能不同域）。若给 `login-url` 增加 `redirect` 参数以支持多回落地址，
**必须同时做白名单校验**——否则该参数就是开放重定向漏洞：攻击者可构造
`login-url?redirect=https://evil.example`，把飞书授权码引到自己的域名。

设计约束（对应 §10 第 4 项）：

- `GET /auth/feishu/login-url?redirect=<url>`
- `redirect` 只在配置的白名单 `FEISHU_REDIRECT_URIS`（列表）内被接受
- 不在白名单内 → **回退到列表首项并记日志**，不报错中断（避免暴露白名单内容）
- 比较前先规范化（去末尾斜杠、域名小写），避免因书写差异误拒
- 保留原 `FEISHU_REDIRECT_URI` 作为 fallback，不破坏现有部署的 `.env`

## 11. 错误处理与降级

- **统一 Toast，直接展示后端 `message`**。后端的校验提示已足够具体
  （如「`approver_type=role` 必须提供 `approver_param`」「`amount_min` 必须小于
  `amount_max`」），中间再包一层笼统文案只会丢信息
- **列表加载失败**：保留用户已设的筛选条件 + 提供重试按钮，不清空页面（免得重填）
- **表单提交失败**：保留用户已填内容；错误定位到具体字段（前端能映射时），
  否则置顶展示后端 `message`
- **同步结果如实回显**：`ok=false` 时展示原因，不提示「成功」
- **危险操作二次确认**：删除规则、触发组织同步，均需在确认框中写明后果
- **不做乐观更新**：审批规则的改动直接影响后续所有单据的审批路由，
  界面上的「快」不值得拿路由正确性换——一律等服务端确认后再刷新列表
- **无离线能力**：管理后台假设内网可达，不做离线缓存（数据敏感且有时效性）

## 12. 测试策略

工具与员工端一致：vitest + @testing-library/react（员工端已装依赖但**零测试**，
本次在管理后台落地，同时回应《项目代码 Review 报告》的覆盖率问题；
需为 `frontend-admin/` 补上 `test` 脚本，员工端当前没有）。

按性价比排序，重点测三类：

1. **纯函数层**（最该测、最好测，也最容易回归）
   - 信封解包（`code === 0` / `code !== 0`）
   - 金额区间文案（含 `min` 不含 `max` / 空值「不限」）
   - 条件摘要渲染（含「且」语义、`in`/`not_in` 的多值展示）
   - 条件预校验（8 个算子、`in`/`not_in` 必须为数组、槽位与值非空）
   - 口径文案（今日 vs 累计至今）、未接入指标的渲染
2. **API 层**：以 mocked axios 覆盖 401、403/40003、业务错误码三个分支
3. **关键交互**：条件构建器的增删行与值类型切换（`in` 时切多值）、
   管理员门禁（非 admin 被拒绝进入）、审计原文展开

**不测**：组件快照测试（维护成本高于收益）。
首期**不引入 Playwright**，以一份手工验收清单替代——把四个模块的关键路径列成勾选项
（放在本方案 §13.3 与交付说明中）。

质量门禁：`tsc -b` + `oxlint` + `vitest run`，与员工端脚本保持一致。

## 13. 部署与运维

### 13.1 部署形态

纯静态产物，nginx 托管；`/api` 反代到后端 8000。

**推荐同域子路径 `/admin/`**（见 §3.3）：复用现有证书与 CORS 配置，运维成本最低。

### 13.2 SPA 子路径的必须配置

子路径部署下需要 `try_files` 兜底，否则**直接刷新** `/admin/approval-rules` 会 404：

```nginx
location /admin/ {
    alias /var/www/admin/;
    try_files $uri $uri/ /admin/index.html;
}
```

同时 `vite.config.ts` 的 `base` 需设为 `/admin/`。

### 13.3 上线检查项

- [ ] 生产构建产物中**不出现「开发登录」区块**（§9.2）
- [ ] 管理后台的回调地址已登记到飞书应用的重定向地址白名单
- [ ] `FEISHU_REDIRECT_URIS` 已配置且包含管理后台回调地址
- [ ] §3.1 的访问范围已确认；若限内网，nginx 已加 IP 白名单
- [ ] 手工验收清单通过（四个模块的关键路径）

## 14. 迭代路线

### 14.1 首期实施顺序建议

首期含「一个新工程 + 四个模块 + 5 项后端改动」，**不建议一次性铺开**。
按「先立骨架、再做最痛的一个模块」的顺序推进，每一步都可独立验收：

| 步 | 内容 | 交付物 |
|----|------|--------|
| S1 | 工程骨架 + API 层 + 登录与管理员门禁 | 能登录、能进空壳主界面，非 admin 被拒 |
| S2 | 后端改动第 4 项（登录多回落地址 + 白名单） | 管理后台在真实飞书环境可登录 |
| S3 | 仪表盘 | 第一个完整模块，验证取数/错误/空态三套通用处理 |
| S4 | 审批规则配置（含条件构建器） | 首期核心价值：规则从脚本改为界面维护 |
| S5 | 组织架构（只读 + 同步 + 主管缺失告警） | 投产前组织核对可用 |
| S6 | 后端改动第 1~3 项 + 审计日志页 | 审计查询满足 SECURITY §6.4 |
| S7 | 测试与上线检查项 | §12 三类测试通过、§13.3 清单勾完 |

组织架构排在审批规则之后、审计之前：它是投产前置，但复杂度低于条件构建器；
审计排最后是因为它的日期筛选与操作者姓名依赖后端改动，且合规要求已由第 1 项覆盖。

### 14.2 二期及以后

按「解投产阻塞优先」排序：

| 顺位 | 内容 | 依赖 |
|------|------|------|
| 1 | 用户清单 + 部门主管维护 + `role` 打标 | 后端补端点；**直接解掉交接文档列为「生产启用审批链前置」的两件非代码事项** |
| 2 | 知识库管理 | 后端补「编辑」接口 |
| 3 | 权限配置 | 后端从零做，需先定权限模型 |
| 4 | 审计导出 | SECURITY §6.4 要求配审批流 |
| 5 | 工具配置持久化 | 后端 `PUT` 当前为空实现 |
| 6 | 审批工作台 / 加签 / 代理审批委派管理 | 后端委派端点已就绪 |
