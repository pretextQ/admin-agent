## 一、环境与依赖管理

### 1.1 Python 环境

本项目要求 Python 3.11+，使用 [uv](https://github.com/astral-sh/uv) 管理虚拟环境与依赖。

```bash
# 安装 uv
pip install uv

# 创建并激活虚拟环境
uv venv
source .venv/bin/activate        # Linux / macOS
.venv\Scripts\activate          # Windows

# 安装运行依赖
uv pip install -r requirements.txt

# 安装开发依赖（含测试、Lint、类型检查）
uv pip install -r requirements-dev.txt
```

> 没有 uv 时可直接用 `python -m venv` + `pip`，两者产出的环境必须一致。

### 1.2 依赖的唯一真相源

**`pyproject.toml` 是依赖的唯一真相源**，`requirements.txt` / `requirements-dev.txt` 只是为不使用 uv 的环境派生的锁文件：

```bash
uv pip compile pyproject.toml -o requirements.txt
uv pip compile --extra dev pyproject.toml -o requirements-dev.txt
```

- 新增依赖必须先改 `pyproject.toml`，再重新生成 lock 文件。
- 禁止只改 `requirements.txt` 而不改 `pyproject.toml`（历史版本曾因此产生三份不一致的依赖清单）。
- 禁止把测试/Lint 依赖写进生产依赖。

## 二、目录与模块结构

### 2.1 目录结构

```text
admin-ai-agent/
├── app/
│   ├── __init__.py
│   └── admin_ai/                 # 主包
│       ├── main.py               # FastAPI 入口
│       ├── config.py             # Settings / get_config()
│       ├── api/                  # 路由层
│       ├── core/                 # 业务核心（agent / rag / tools / rules / auth）
│       ├── db/                   # database.py / models.py / schemas.py / orm/
│       ├── services/             # 服务层
│       ├── middleware/           # 中间件
│       └── utils/                # 通用工具
├── migrations/                   # Alembic 迁移（根目录，与 alembic.ini 同级）
├── tests/
│   ├── conftest.py
│   └── admin_ai/                 # 与主包同构
├── scripts/
├── docs/
├── alembic.ini
├── pyproject.toml
└── README.md
```

**硬性约束：**

- 主包是 `app/admin_ai/`，所有本地导入形如 `from app.admin_ai.xxx import yyy`。
- 迁移目录固定在仓库根 `migrations/`。
- 测试目录 `tests/admin_ai/` 与主包同构。

### 2.2 分层依赖方向

```text
api  →  services  →  core  →  db
                 ↘  utils
```

- `api` 只做参数校验、鉴权、调用 service、组装响应，不写业务逻辑。
- `services` 编排 `core` 能力与持久化。
- `core` 不依赖 `api`；`db` 不依赖上层。
- 禁止跨层反向依赖（例如 `core` 里 import `api`）。

### 2.3 文件粒度

- 单个文件建议不超过 400 行；超过说明职责过多，应拆分。
- 一个文件一个主要类或一组紧密相关函数。

## 三、代码风格

代码风格以 [代码风格指南](./代码风格指南.md) 为准，核心要求如下：

| 维度 | 要求 |
|------|------|
| 格式 | Ruff format，行宽 100，4 空格缩进，双引号 |
| 导入 | 标准库 → 第三方 → 本地；绝对导入；禁通配符 |
| 类型注解 | 所有公共函数必须完整注解；可空用 `Optional[T]` |
| 数据容器 | 内部用 `@dataclass`，API/配置用 Pydantic |
| 枚举 | `class X(str, Enum)` |
| 文档字符串 | Google 风格，模块/公共类/公共方法必备 |
| 异步 | I/O 全异步；禁止在 `async def` 中阻塞 |
| 错误处理 | 具体异常 + `raise ... from`；预期失败用结果对象 |
| ORM | SQLAlchemy 2.0 `Mapped` / `mapped_column` |
| 日志 | structlog / logging，禁止 `print()` |

### 3.1 工程硬约定（踩坑沉淀）

以下约定来自真实联调中暴露的问题，新增代码必须遵守：

| 主题 | 约定 | 原因 |
|------|------|------|
| 时间 | 一律使用 `db/models.py` 的 `utc_now()`（无时区 UTC），禁止 `datetime.utcnow()` 与带时区 `now(timezone.utc)` 混用 | 列类型为 `TIMESTAMP WITHOUT TIME ZONE`，混用产生时区偏移错误 |
| 枚举列 | `SAEnum(X, values_callable=lambda x: [e.value for e in x])` | 原生 PG 枚举按 value（小写）创建，SAEnum 默认绑定 name（大写）导致写入必败 |
| Redis | 所有 `from_url` 显式 `protocol=2` | redis-py 8 默认 RESP3 握手，Redis 5（Windows 版）拒绝 `HELLO` |
| Redis 连接 | 统一走 `db/redis.py` 的单例，禁止每次请求 `redis.from_url()` 新建 | 连接复用 |
| 写库提交 | 写接口在端点内显式 `await db.commit()`，不要依赖 `get_db_session` teardown | teardown 提交发生在响应发送之后，紧随其后的读请求会读到提交前快照 |
| 外部调用 | Chroma 等同步客户端必须 `asyncio.to_thread` 包裹并加超时（`RAG_TIMEOUT_SECONDS=30`） | 首次嵌入模型加载可能长时间挂起，阻塞事件循环 |
| 中间件 | 新中间件必须同步注册到 `main.py`（TraceId 最外层） | 出现过"中间件写好未注册、审计表永远为空"的缺陷 |
| 管理接口 | 所有 `/admin/*` 端点必须挂 `get_admin_user` | 曾出现管理接口无鉴权裸奔 |
| 会话属主 | 会话状态（`ConversationState`）必须记录 `user_id`，读/确认前校验属主 | 高风险操作曾可被任意登录用户代确认 |
| Shell 脚本 | 项目内 `.sh` 一律 LF 行尾，由 `.gitattributes` 的 `*.sh text eol=lf` 锁定 | 本机 `core.autocrlf=true`，否则换机器 clone 出的脚本报 `\r: command not found` 无法执行 |
| Windows 命令路径 | 调 Windows 原生程序（`psql`/`pg_ctl`/`initdb` 等）前 `export MSYS_NO_PATHCONV=1`，路径写 `D:/xxx` 而非 `/d/xxx` | Git Bash 会把 `/d/...` 当盘符相对路径处理，数据/文件会落到 `D:\d\...` 等意外位置 |
| psql 中文数据 | 导入含中文的 SQL 必须 `export PGCLIENTENCODING=UTF8` | Windows 下 psql 客户端编码非 UTF8 时报 `invalid byte sequence for encoding "UTF8"` |
| 密钥 | 任何 Key/密码只放本地 `.env`（已 gitignore），禁止写入代码、文档、脚本、测试固件或提交信息 | 仓库公开，Key 进入历史后即使删除也可读出，只能去服务商轮换 |
| LLM 调用 | 一律经 `LLMGateway.chat()`（`core/llm_gateway.py`），禁止直接持有 `AsyncOpenAI` 或调用 `chat.completions.create`；调用须带 `purpose` 与 `session_key` | 绕过网关即绕过脱敏、L4 拦截与调用审计；`session_key` 缺失会使占位符跨会话编号混乱（同轮对话内出现两个占位符指向同一人） |
| 日志内容 | 日志只记长度、ID、类别等非内容字段；**禁止**打印用户消息原文、槽位值、金额、身份信息 | 对话属 L3 个人数据，SECURITY §6.2 禁止日志写入明文；曾有编排器打印消息前 50 字的前科 |
| 审批人来源 | 高风险任务的审批链一律由 `core/approval` 按 `approval_rules` 路由（禁止硬编码取管理员）；解析不出审批人时转人工指派并记录原因（`task.data._routing`），**不得猜测** | 历史实现取「首个管理员」审批，与场景文档 APR-001/002 的金额分级相差一整个层级体系，审批结果不具备公司内部授权效力（评审 B-2） |
| 审批规则 | 规则用 `scripts/manage_approval_rules.py` 或 `/admin/approval-rules` 维护，不要改代码；审批步骤模式（任一人/会签）随审批链快照到 `approvals.mode` | 规则硬编码进业务逻辑后无法由行政/财务自助调整；快照保证在途审批不受规则事后修改影响 |
| 规则条件 | 按槽位分支用 `approval_rules.condition`（受限算子，勿自行解析表达式）；**槽位缺失即条件不成立**，所以「无论何时都要审批」的业务必须配一条兜底规则（区间与条件都为空） | 缺失即不成立是为「不猜测」；兜底规则保证不会被条件漏判而静默放行 |
| 审批清单 | 是否走审批由 `APPROVAL_REQUIRED_BUSINESS_TYPES` 配置决定，与二次确认（`HIGH_RISK_BUSINESS`）是两件事：前者影响任务是否进 `approving`，后者决定是否弹确认卡片 | 曾把两者混为一谈，导致请假等业务即使场景要求审批也「提交即完成」 |
| 组织数据 | 部门与汇报线以 HR 为权威源同步（`scripts/sync_org.py`），不在本系统重复维护；同步失败沿用上次快照，绝不清空 | 两套真相会导致审批路由到错误的层级（评审 B-2 / 设计 §3） |
| 数据归属 | 查询类接口必须把归属条件下推到 SQL（`core/approval/ownership.py` 的 `build_ownership_plan`），禁止「先查全量再过滤」；越范围查询（`dept`/`all`）记审计 | SECURITY §4.3 最小权限原则；内存过滤会先读到无权限的数据 |
| 占位标记 | 编排器返回的 `needs_*` 标记（`needs_rag` / `needs_status_query`）必须在同一批次内接上消费方（API 层或编排器自身），禁止只留标记 | 历史上 `status_query` 的标记长期无人消费，用户看到的一直是「正在为您查询状态…」占位话术；`policy_query` 的 `needs_rag` 曾有同类问题 |
| 识别与聚合分离 | 编排器不持有数据库会话：只做意图/槽位/查询类型识别与工具调用，需要查库聚合的只读查询（如状态查询）在 API 层用独立服务执行（`core/status_query.py`） | 编排器在 lifespan 中构造一次、无请求级会话；把查询硬塞进编排器会导致要么长持会话，要么绕过归属校验 |
| 集成测试 | 需要真实 PG 的用例打 `@pytest.mark.integration`，并在模块内加 dispose 引擎的 autouse fixture；直连落库时按依赖顺序分步 `flush()`（先 users 再 departments） | pytest-asyncio 每个用例新建事件循环，全局引擎连接池会绑定到已关闭的循环（`Event loop is closed`）；一次 flush 内的插入顺序不完全可控，会触发外键违规 |

## 四、Git 规范

### 4.1 分支策略

```text
main          ← 生产分支，只接受 PR
  └── develop ← 开发分支
       ├── feature/xxx  ← 功能分支
       ├── bugfix/xxx   ← Bug 修复
       └── hotfix/xxx   ← 紧急修复
```

- `main` 与 `develop` 开启分支保护，禁止直接 push。
- 功能分支从 `develop` 切出，合并后删除。

### 4.2 Commit 规范

格式：`<type>(<scope>): <summary>`

| type | 说明 |
|------|------|
| `feat` | 新功能 |
| `fix` | Bug 修复 |
| `docs` | 文档 |
| `refactor` | 重构（不改变外部行为） |
| `test` | 测试 |
| `chore` | 构建/工具 |

`scope` 取值：`config`、`api`、`agent`、`rag`、`tools`、`rules`、`approval`、`auth`、`db`、`middleware`、`docs`。

```text
feat(agent): 支持请假意图的多轮槽位补全
fix(db): 修复列名与 SQLAlchemy 保留属性冲突
docs(api): 补充统一响应信封说明
```

- 一个 commit 只做一件事；不要混入格式化无关文件的改动。

### 4.3 PR 规范

- 每个 PR 至少 1 人评审。
- PR 描述使用 [CONTRIBUTING.md](../../CONTRIBUTING.md) 中的模板。
- CI 未通过不允许合并。

## 五、API 设计规范

### 5.1 RESTful 约定

```text
GET    /api/v1/tasks             # 列表
GET    /api/v1/tasks/{id}        # 详情
POST   /api/v1/chat/send         # 业务动作
POST   /api/v1/tasks/{id}/approve
```

- 资源用复数名词；动作用 POST + 动词。
- 路径与字段一律 `snake_case`。
- 分页统一 `page` / `page_size`，响应带 `total`。

### 5.2 统一响应信封

**成功：**

```json
{ "code": 0, "message": "success", "data": { } }
```

**失败：**

```json
{ "code": 40001, "message": "参数错误", "details": { "field": "message" } }
```

- 由全局异常处理器统一包装，路由代码直接返回数据对象即可（见 [代码风格指南](./代码风格指南.md) 第 14 节）。
- HTTP 状态码仍需语义化，不能一律返回 200。

### 5.3 错误码

| 错误码 | 含义 | HTTP 状态码 |
|--------|------|-------------|
| 0 | 成功 | 200 |
| 40001 | 参数错误 | 400 |
| 40002 | 未授权 | 401 |
| 40003 | 无权限 | 403 |
| 40004 | 资源不存在 | 404 |
| 40005 | 请求过于频繁 | 429 |
| 50001 | 内部错误 | 500 |
| 50002 | 外部服务错误 | 502 |
| 50003 | 服务不可用 | 503 |

### 5.4 接口版本与兼容

- 路径带版本号 `/api/v1`。
- 字段只增不删；删除字段必须先标记 deprecated 并在 CHANGELOG 记录。

## 六、数据库规范

### 6.1 表与模型

```python
class UserModel(Base):
    """用户模型。"""

    __tablename__ = "users"

    id: Mapped[str] = mapped_column(String(36), primary_key=True, default=generate_uuid)
    employee_id: Mapped[str] = mapped_column(String(50), unique=True, index=True, nullable=False)
    is_deleted: Mapped[bool] = mapped_column(Boolean, default=False, nullable=False)
    created_at: Mapped[datetime] = mapped_column(DateTime, default=datetime.utcnow, nullable=False)
    updated_at: Mapped[datetime] = mapped_column(
        DateTime, default=datetime.utcnow, onupdate=datetime.utcnow, nullable=False
    )
```

| 规范 | 说明 |
|------|------|
| 主键 | UUID 字符串（`String(36)`） |
| 表名 | 小写下划线、复数 |
| 列名 | 小写下划线；禁用 `metadata`，用 `meta` |
| 审计字段 | `created_at` / `updated_at` 必须有；`updated_at` 带 `onupdate` |
| 软删除 | 统一 `is_deleted`，查询默认过滤 |
| 金额 | 用 `Numeric(12, 2)` 或整数「分」，**禁止 float** |
| 时间 | 存 UTC，展示层转 `Asia/Shanghai` |
| 索引 | 高频查询/外键字段建索引；复合索引命名 `idx_<表>_<字段...>` |

### 6.2 迁移

```bash
# 生成迁移（在仓库根执行，使用 ./migrations）
alembic revision --autogenerate -m "add users table"

# 升级 / 回滚
alembic upgrade head
alembic downgrade -1
```

- 表结构只能由 Alembic 变更；**生产环境禁止 `Base.metadata.create_all`**。
- 每个迁移必须能回滚（提供 `downgrade()`）。
- 大表变更遵循「先加列 → 回填 → 再加约束」的向后兼容顺序。

## 七、配置规范

### 7.1 配置来源

- 运行期配置集中在 `app/admin_ai/config.py` 的 `Settings`（pydantic-settings），通过 `get_config()` 获取单例。
- 本地开发用根目录 `.env`；示例见 `.env.example`。
- 新增配置项必须同步更新 `.env.example` 与部署文档。

### 7.2 环境变量命名

- 统一 `SCREAMING_SNAKE_CASE`，按模块前缀分组（`LLM_`、`CHROMA_`、`OA_`）。
- 禁止在代码中硬编码环境相关值（地址、密钥、开关）。
- 生产环境启动时校验：若 `SECRET_KEY` 仍为默认值则**拒绝启动**。

### 7.3 密钥管理

- 密钥只通过环境变量注入，禁止提交到仓库。
- 日志中必须脱敏，只打印掩码或前后各 4 位。

## 八、安全规范

### 8.1 权限继承

- 运行期动作必须使用**已认证用户**的身份访问上游系统，禁止用管理员身份代执行。
- 敏感操作（打款、用印、导出、批量删除）必须二次确认并留痕。
- 所有资源访问必须校验归属（禁止只按 id 查询而不校验 user_id）。

### 8.2 输入校验

- 所有外部输入在系统边界校验（Pydantic + 业务规则），不信任 LLM 生成的参数。
- 工具调用前必须校验参数白名单与权限范围，防止提示注入导致越权调用。

### 8.3 传输与存储

- 生产强制 HTTPS/WSS。
- 敏感字段（身份证、银行账号、密钥）加密存储。
- 上传文件校验类型、大小并做病毒扫描。

### 8.4 WebSocket 鉴权

- **禁止把 JWT 放在 WebSocket URL**（会进入网关访问日志）。
- 使用 `Sec-WebSocket-Protocol` 携带 token，或先通过 HTTP 换取一次性 ticket。

## 九、日志与可观测性

### 9.1 结构化日志

```python
import structlog

logger = structlog.get_logger(__name__)
logger.info("消息处理完成", user_id=user_id, intent=intent, duration_ms=duration)
```

必须包含的上下文：`request_id`、`user_id`、`conversation_id`、`intent`、`duration_ms`。

### 9.2 指标与健康检查

- `/metrics` 暴露 Prometheus 指标（调用次数、延迟、Token 成本、转人工率）。
- `/api/health` 返回 `{"status": "healthy"}`，供容器健康检查与网关探活使用。
- 关键 SLO：首响应 < 3s、关键路径可用性 ≥ 99.5%、错误率 < 1%。

### 9.3 审计

- 全量记录「输入 → 决策 → 调用 → 返回 → 操作人」，审计覆盖率要求 100%。
- 审计日志不得包含未脱敏敏感信息。

```text
tests/
├── conftest.py
└── admin_ai/
    ├── test_api/test_<module>.py
```

```bash
pytest tests/admin_ai -q

```

### 10.3 标记

必须在 `conftest.py` 的 `pytest_configure` 注册并通过 `--strict-markers` 校验：

| marker | 用途 |
|--------|------|
| `slow` | 耗时超过 1 秒 |
| `integration` | 依赖外部服务 |
| `e2e` | 全链路 |
| `llm` | 需要真实 LLM 调用 |

### 10.4 测试原则

- 单元测试不依赖真实网络、真实数据库、真实 LLM（用 mock/stub）。
- 外部系统用 `respx` 打桩 httpx，LLM 用固定响应夹具。
- 新增功能必须同时提交测试；Bug 修复先写复现测试。

## 十二、工具链

```bash
# 格式化 + Lint
ruff format app/ tests/
ruff check --fix app/ tests/

# 类型检查
mypy app/

# 测试
pytest tests/admin_ai -q

# 一键检查（等价于 CI 的门槛）
ruff format --check app/ tests/ && ruff check app/ tests/ && mypy app/ && pytest -q
```

`.pre-commit-config.yaml` 至少包含 `ruff`（含 `--fix`）、`ruff-format`、`mypy` 三个钩子。

> 工具链不包含 Black / isort / flake8，其能力由 Ruff 统一覆盖。

## 十三、代码评审清单

评审者按以下维度检查：

**正确性**

- [ ] 所有函数有类型注解，类型与实现一致
- [ ] I/O 均为异步，无阻塞调用
- [ ] 无裸 `except`，异常保留 `from`
- [ ] 边界条件（空值、超长、并发）有处理

**安全**

- [ ] 无硬编码密钥
- [ ] 运行期动作继承已认证用户权限，无越权
- [ ] 资源访问校验归属
- [ ] 输入已校验，工具参数有白名单
- [ ] 日志无敏感信息

**架构**

- [ ] 分层依赖方向正确，无反向依赖
- [ ] 新组件按注册中心/策略/适配器模式接入，无散落分支
- [ ] 配置项集中管理，无硬编码

**测试**

- [ ] 新增功能有测试，Bug 修复有复现测试
- [ ] 覆盖率达标
- [ ] 异步测试标记正确

**文档与风格**

- [ ] 公共接口有 docstring
- [ ] 相关文档已同步更新
- [ ] 通过 Ruff / mypy / pytest
