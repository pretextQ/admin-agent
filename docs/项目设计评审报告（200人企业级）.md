# 设计文档评审报告（200 人企业级视角）

> 评审日期：2026-09-20　|　评审范围：需求文档、技术架构、API 规范、前端方案、11 个业务场景、测试计划、部署与运维、安全策略、上线指南
> 评审视角：**200 人规模企业**的生产上线可行性

## 一、总体评价

设计文档的**完备度显著高于同类项目**：数据分级（L1~L4）、PII 清单与保留期、审批混合架构、SLO 与告警阈值、
备份 RTO/RPO、Expand/Contract 迁移原则、LLM 成本控制手段、提示注入防护都已成体系。
11 个业务场景文档细到"发票查重/OCR 识别/金额分级审批/软硬阻断"级别，可直接作为开发依据。

**主要问题集中在两处**：① 涉及外部 LLM 的数据合规链路没有打通；② 组织架构与权限模型不足以支撑真实的
企业审批（设计与数据模型脱节）。另有若干文档间口径不一致，会让实现方与验收方"各说各话"。

## 二、阻断级（上线前必须解决）

### B-1　L3 敏感数据进入外部 LLM，缺脱敏与合规设计

> 📐 **设计补丁已产出**：[LLM 数据脱敏与合规设计](architecture/LLM数据脱敏与合规设计.md)
> （含送出白名单、脱敏层与占位符回填、DPA 三要素、调用审计、拦截与降级、T-1~T-9 测试要点）

**现状**：`SECURITY.md` §3.2 明确「**L4** 数据不得进入日志、缓存明文、向量库与 LLM Prompt」，
但 L3（员工姓名/工号、假期余额、报销金额、发票影像、**对话内容**）无同等约束。
而当前实现中，用户原话与抽取出的槽位（含金额、姓名）会**原样发给外部 LLM**——
意图识别、槽位抽取、回复生成三条链路都是如此。

**风险**（对 200 人企业是实质风险，非理论风险）：

- 员工说「我要请病假，附诊断证明」「报销 8000 元客户招待费」，这些文本与金额都离开了公司边界；
- PIPL 下这属于**委托第三方处理个人信息**，需履行告知同意、签订数据处理协议（DPA）并监督受托方；
- 供应商侧是否留存、是否用于训练、留存多久——文档未做任何约束；
- 一旦发生争议，"哪些数据发给了谁"无法自证（审计只覆盖本地库）。

**建议**：

1. 在 `SECURITY.md` 增补「LLM 数据出境/出域」章节，明确**送 LLM 的数据范围白名单**：
   只送完成任务所必需的最小字段，L3 中可识别的直接身份信息（姓名、工号、手机号）一律**先脱敏再送**
   （如 `张三`→`员工A`、`138****5678`），金额可按需送但需在 DPA 中约定；
2. 建立**脱敏层**（建议放在 `core/llm.py` 与各调用点之间，形成统一出入口），而不是靠每个调用方自觉；
3. 与 LLM 供应商签署数据处理协议，确认「不用于训练、留存期限、可删除」三项；
4. 评估**本地化模型**作为涉密场景的备选（如证明开具、合同用印），与 `§7 P0-1` 的嵌入模型选型一并考虑；
5. 在审计中记录**每次 LLM 调用的数据范围摘要**（送了哪些字段类别，不含值），使对外披露可自证。

> 这是当前文档体系里**唯一会直接导致合规不通过**的缺口，建议优先处理。

### B-2　组织架构与审批权限模型不足以支撑真实企业

> 📐 **设计补丁已产出**：[组织架构与审批路由设计](architecture/组织架构与审批路由设计.md)
> （含 departments/approval_rules/approval_delegations 三表、路由算法与自审拦截、
> 上游同步与失败降级、数据归属注入、Expand/Contract 迁移、T-1~T-10 测试要点）
>
> ✅ **已实现（2026-09-20）**：补丁末尾 5 项未决事项已由业务方拍板（2~3 层单法人 / 任一人通过 /
> HR 为权威源 / 首期做代理审批 / 脚本+API 维护），并落地为：三张新表 + 迁移 `002`（Expand + 回填）、
> 纯函数路由算法（自审拦截与上溯、停用上溯、链内去重、委派替换）、
> `chat.py` 确认路径改为按规则路由（解析不出则转人工指派，不猜测）、
> 审批流转支持任一人/会签、`/tasks/my?scope=dept|all` 数据归属注入（dept/all 记审计）、
> HR 组织同步（http + CSV 降级，失败沿用旧快照）。
> 证据：真实 PG 集成用例（路由算法 6 + 场景覆盖 10 等）、`pytest` 全绿、
> E2E 冒烟（改为跨用户：员工 emp999 提交 → 主管 admin001 审批）。
> 后续批次持续补测，当前基线为 `304 passed, 27 deselected` / 集成 27 / E2E 11 步。
> 剩余：T-10 双读校验期未安排（Cutover 在同一次发布内完成）、§6 组织缓存留待压测后评估、
> 旧列 `users.department` 的 Contract 阶段另排。详见设计补丁 §12「实现状态与偏离」。

**现状**：`users` 表只有 `department`（字符串）与 `role`（字符串）两个字段，**没有部门表、没有汇报线、
没有成本中心**。而业务场景文档要求的是真审批：

- `07-报销申请.md` §5.3：`APR-001` 单笔 ≤2000 元主管审批；`APR-002` >2000 元**总监审批 → 主管审批**；
  `APR-003` 超标准差旅需特批；
- `SECURITY.md` §4.3：每次工具调用须按「角色 + 数据归属 + **金额/范围**」判定权限，
  查询须注入「本人/本部门」归属条件。

**问题**：文档要求按金额分级、按部门归属路由审批人，但**数据模型无法回答「谁是我的主管」「谁是本部门总监」**。
当前实现退化为「首个管理员审批」，与设计要求相差一个数量级。

**建议**：

1. 补一张 `departments` 表（`id / name / parent_id / path`）支持部门树，`users.department_id` 外键指向它；
2. 补审批路由规则的可配置化设计（不在代码里硬编码"主管/总监"）：
   `approval_rules(business_type, amount_min, amount_max, approver_role_or_user, step_order)`；
3. 明确**汇报线获取方式**：200 人企业通常已在 HR/OA 系统维护汇报关系，建议从上游同步而非本地重建，
   并在文档中写清同步频率与失败降级（同步失败时转人工，不猜审批人）；
4. 补**代理审批/委派**设计（主管休假是高频场景，200 人企业必然遇到）；
5. 组织架构也要进缓存策略（`部署与运维.md` §8.3 已有 `rbac:{user_id}` 5 分钟 TTL，补上组织信息即可）。

### B-3　性能口径三处不一致，且与 LLM 调用特性冲突

> ✅ **已解决（2026-09-20）**：需求文档 §6.1 重写为基准（200 人基线 +
> 响应时间分级 + 峰值场景 + 错误率），部署 §8.1 与测试计划 §6.1 已同步；
> 部署 §8.2 补成本代入与「合并意图+槽位调用」的省时省钱提示。
> 以下为原始评审记录，留档备查。

**现状**：

| 来源 | 口径 |
| --- | --- |
| `需求文档.md` §6.1 | 并发用户数 ≥ 100，首响应 ≤ 3s |
| `部署与运维.md` §8.1 | 日活 1000 → 3000，峰值 QPS 50 → 150，首响应预算「LLM ≤1.5s + 检索 ≤0.5s + 其他 ≤1s」 |
| `测试计划.md` §6.1 | 并发 ≥ 100，QPS ≥ 50 |

三处数字对不上，且**都没有以「200 人」为基线推导**——部署文档按 1000~3000 日活规划，对 200 人企业属于过度设计；
PRD 的「并发 ≥100」又缺少推导依据（200 人企业 20% 同时在线约 40 人）。

更关键的是**首响应 ≤3s 与 LLM 调用次数冲突**：当前链路中意图识别、槽位抽取、回复生成是**三次独立 LLM 调用**，
若串行执行，仅 LLM 就 2~6s，预算的「LLM ≤1.5s」只在单次调用下成立。

**建议**：

1. 统一性能口径，并给出**基于 200 人的推导**：
   日活 200 × 人均 3 轮 = 600 轮/日；峰值集中在 08:30-09:30 与月末（建议按均值 5~10 倍取峰值 QPS）；
2. 明确**峰值场景**（这是企业级设计的必备项）：早高峰集中请假/查余额、月末集中报销、制度更新后的问答洪峰；
3. 针对首响应预算，给出**合并调用**方案：意图识别 + 槽位抽取合并为一次 LLM 调用（当前两次），
   或对小模型/规则可判定的场景跳过 LLM（现有规则回退已具备该能力，需明确**触发条件**以省时省钱）；
4. 补**响应时间的分级目标**：简单问答（纯检索/规则）≤1.5s、需 LLM 生成 ≤5s、含下游工具调用 ≤10s，
   避免"一刀切 3s"导致验收争议。

## 三、重要改进（影响可运营性与成本）

### I-1　知识库运营设计缺失（200 人企业的高频痛点）

PRD 仅在 §2.2 写「制度知识库需提前录入并保持更新」，没有回答：**谁维护、多久更新、过期怎么发现、谁来审**。
200 人企业的制度更新是常态（政策调整、假期规则变化），且**错误的制度回答会被员工当作依据**，风险高于"答不出来"。

**建议**：补「知识库运营规范」——维护责任人（行政专员）、更新触发（制度发文后 N 个工作日内）、
审核流程（发布前双人复核）、**有效期字段与到期提醒**（`knowledge_docs` 增加 `valid_until`）、
以及**命中率与差评率看板**（否则无法知道知识库是否在退化）。

### I-2　LLM 供应商依赖与切换未设计

当前单一供应商（DeepSeek），文档未讨论：供应商涨价/停服/合规政策变化/模型下线时的应对。
项目已有 `core/llm.py` 工厂（OpenAI 兼容协议）作为基础，但缺设计层面的**双供应商与降级**说明。

**建议**：文档补「供应商可替换性」一节——主备供应商配置、切换耗时目标（建议 ≤1 小时）、
以及**能力降级矩阵**（LLM 不可用时：意图→规则回退、回复→模板、制度问答→直接返回检索原文）。

### I-3　管理后台的设计与前端方案矛盾

PRD §5.6 明确要求「系统管理模块」（知识库管理、权限配置、审计日志），
但 `前端技术方案设计.md` 把「管理后台」标为 **P2 待下个迭代**。

**建议**：明确管理后台的**上线归属**——若首期不做 UI，需在 PRD 中标注"首期通过 API/脚本管理"，
并列出可接受的操作方式（否则行政专员无法维护知识库，系统会很快停止更新而失效）。

### I-4　外部 OA 不可用时的降级路径未定义

`架构设计` §2.4 的回调 + 5 分钟轮询设计完善，但未定义**OA 长时间不可用**时的行为：
审批全部卡在 `approving`？是否允许本地临时审批？

**建议**：补「外部系统故障降级矩阵」，逐一定义 OA/财务/物资/HR 不可用时的用户可见行为与恢复后的一致性处理
（建议：只读降级 + 明确告知 + 恢复后补同步，禁止本地双写产生两套真相）。

### I-5　多轮对话的上下文与成本策略偏薄

`部署与运维.md` §8.2 提到「仅取最近 5 轮」作为降本手段，但未定义：会话超时（多久算新会话）、
跨设备续接、长会话的摘要压缩、以及**每会话的 Token 上限**。

**建议**：补会话生命周期设计（建议 Redis TTL 24 小时已具备，需明确"超时后新建会话并提示"），
并对长对话引入摘要（把早期轮次压缩为摘要，而非直接丢弃）。

## 六、值得肯定的设计（建议保持）

1. **数据分级与 PII 清单**（SECURITY §3）：L1~L4 分级 + 采集场景 + 存储位置 + 脱敏方式 + 保留期限，
   可直接用于合规自评；这是很多成熟项目都缺失的部分。
2. **最小权限原则**（SECURITY §4.3）：「智能体不拥有超越用户本人的权限」+
   优先使用用户委托令牌（On-Behalf-Of）而非全权服务账号——这个设计在 Agent 类系统中属于高水平。
3. **审批混合架构**（架构 §2.3/2.4）：不重建审批引擎、本地存快照、回调 + 轮询双保险、`external_approval_id` 幂等，
   务实且可落地。
4. **扩展/收缩迁移原则**（部署 §5.4）：为不停机发布与回滚提供了明确约束。
5. **LLM 成本控制的五项手段**（部署 §8.2）：分级模型、缓存、Prompt 精简、预算熔断、指标闭环，
   覆盖了成本治理的主要抓手。
6. **场景文档的规则化**：以 `INV-xxx`/`STD-xxx`/`APR-xxx` 编号承载业务规则并标注阻断级别，
   便于测试用例与规则引擎双向追溯。
