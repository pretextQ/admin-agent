**核心数据流**（都真实落库）：

```
POST /chat/send → 状态恢复(Redis) → 意图(LLM/规则) → 槽位抽取(LLM/规则) → 不全则反问
  → 规则校验 → 高风险(expense/seal)出确认卡片 → /chat/confirm 恢复执行
  → 工具 HTTP 转发(8001-8003 桩) → 成功: 任务落库(低风险 COMPLETED / 高风险 APPROVING + 按规则路由审批链)
  → LLM 生成自然语言回复(_compose_reply，不可用时回退模板"操作已完成")
  → 会话+消息落库 → 响应

审批路由（B-2）：高风险任务 → 按「业务类型 + 金额 + 申请人部门」匹配 approval_rules
  → 解析审批人（本部门/上级部门/顶层主管、角色、指定人）→ 自审拦截与上溯 → 链内去重 → 委派替换
  → 生成审批链（任一人通过 / 会签）→ 审批人 /tasks/pending-approval 可见
  解析不出审批人时：任务置 processing + task.data._routing 记原因 + 通知行政专员（绝不猜测审批人）

转人工：POST /chat/transfer → 校验属主 → 会话置 transferred → 消息落库 → 清待确认 → 通知
无法识别意图时编排器也会自动转人工（该路径未调通知服务，见 §7）

状态查询（Batch 15）：status_query → 编排器只识别查询类型（缺则追问）/单据号
  → API 层 StatusQueryService 按 user_id 查本人在时间窗内的 tasks/approvals（-m integration 已验）
  → 格式化回复（进度/余额/单据详情）+ 落 status_query 审计（只记类型与条数）
  → 只读：不建任务、不改状态、不调业务工具
```

## 五、工程硬约定（违反会翻车，全部有前科）

详见 `docs/guides/开发规范.md` §3.1，速记：

1. **时间**一律 `from app.admin_ai.db.models import utc_now`，禁止 `datetime.utcnow()` / `now(timezone.utc)` 混用（jwt 签发除外，那里必须 aware）。
2. **模型枚举列**必须 `SAEnum(X, values_callable=lambda x: [e.value for e in x])`——PG 原生枚举是小写 value，SAEnum 默认绑大写 name，不写这个任务表写入直接报错。
3. **Redis** 所有 `from_url` 显式 `protocol=2`；连接走 `db/redis.py` 单例。
4. **写接口端点内显式 `await db.commit()`**——依赖 teardown 的提交在响应之后，会造成读写竞态。
5. Chroma 等同步客户端必须 `asyncio.to_thread` + 超时（`RAG_TIMEOUT_SECONDS=30`）。
6. 新中间件必须注册进 `main.py`（TraceId 最外层）；`/admin/*` 必须挂 `get_admin_user`；会话状态必须校验属主。
7. 分页统计用 `db.scalar(select(func.count())...)` 全量集合，不要对当前页做 Python 计数。
8. **密钥只留本地 `.env`**（已 gitignore），禁止写进代码/文档/脚本/测试/提交信息——仓库公开，
   一旦进历史就只能去服务商轮换（提交前用 `git diff | grep -E "sk-[A-Za-z0-9]{20,}"` 自查）。
9. **`.sh` 必须 LF 行尾**（`.gitattributes` 已锁 `*.sh text eol=lf`）——本机 `core.autocrlf=true`，
   否则换机器 clone 出的脚本报 `\r: command not found`。
10. **调 Windows 原生程序**（`psql`/`pg_ctl`/`initdb`）前 `export MSYS_NO_PATHCONV=1` 且路径写 `D:/xxx`；
    导入含中文的 SQL 还要 `export PGCLIENTENCODING=UTF8`（两条都已内置到 `scripts/db_backup.sh`）。
11. **LLM 调用必须可降级**：新增 LLM 依赖的功能，未配 Key 或调用失败时要有回退路径，不得阻断业务
    （参考 `Orchestrator._compose_reply` 的 try/except + 模板回退）。
12. **LLM 调用必须经 `LLMGateway`**：禁止直接持有供应商客户端（`AsyncOpenAI`）或用 `chat.completions.create`——
    绕过网关即绕过脱敏、L4 拦截与调用审计，属合规缺口。调用时须传 `purpose` 与 `session_key`
    （会话 ID，用于占位符会话内一致）。
13. **审批人必须由路由算出**：禁止在业务代码里硬编码审批人（历史实现取「首个管理员」，与 APR-001/002 不符）。
    高风险任务的审批链一律走 `core/approval`（规则匹配 → 解析 → 自审拦截 → 去重 → 委派），
    解析不出时转人工指派并记录原因（`task.data._routing`），**绝不猜测审批人**。
    规则用 `scripts/manage_approval_rules.py` 或 `/admin/approval-rules` 维护，不要改代码。
    按槽位分支用 `rule.condition`（受限算子）；**槽位缺失即条件不成立**，需要「无论如何都审批」就配兜底规则；
    另外「是否走审批」由 `APPROVAL_REQUIRED_BUSINESS_TYPES` 决定，与二次确认卡片是两件事。

## 六、环境踩坑速查（本机实测）

| 症状 | 原因与解法 |
|------|-----------|
| PG 起不来："administrative permissions is not permitted" | PG 拒绝管理员账户。当前用普通用户 + 绿色二进制方式，勿用管理员身份跑 `postgres.exe` |
| `initdb -D /d/NF/...` 报成功但目录找不到 | MSYS 把 `/d/...` 当盘符相对路径，实际建到 `D:\d\NF\...`。先用 `export MSYS_NO_PATHCONV=1`，路径写 `D:/NF/...` |
| Redis 起不来："listen: 提供了一个无效的参数" | 少了 `--bind 127.0.0.1` |
| 运行时报 `unknown command 'HELLO', with args beginning with: '3'` | redis-py 8 RESP3 vs Redis 5，需 `protocol=2`（已全改，新增连接点要记得加） |
| 任务列表计数为 0 但明细有数据 | teardown 提交竞态，写接口要显式 commit |
| Windows 枚举值无效 `对于枚举taskstatus的输入值无效: "PENDING"` | 见硬约定 #2 |
| `pnpm build` 报 `'node' 不是内部或外部命令` | Windows 系统 PATH 没有 nodejs（仅 Git Bash 注入）。`export PATH="/c/Program Files/nodejs:$PATH"` |
| `psql -f /d/NF/...` 报 `No such file or directory` | psql 是 Windows 程序，MSYS 路径被当盘符相对路径。用 `cygpath -w` 转成 `D:\NF\...`（`scripts/db_backup.sh` 已内置） |
| 导入含中文的 SQL 报 `invalid byte sequence for encoding "UTF8"` | Windows 下 psql 客户端编码不是 UTF8。`export PGCLIENTENCODING=UTF8`（`scripts/db_backup.sh` 已内置） |
| Git Bash 里 Windows 命令报路径错误 | `export MSYS_NO_PATHCONV=1` |
| 系统只有 Python 3.8，本项目要求 ≥3.11 | 用 `D:\NF\Tools\uv.exe` 隔离装 3.12（或直接跑 `scripts/setup_dev_env.sh`），**不要**升级/污染系统 Python 3.8（用户其他工作依赖它） |
| corepack/npm 下载 pnpm 超时、chroma 嵌入模型下载卡死 | 国际网络受限。pnpm 用 npmmirror；chroma 探活超时 10s 后自动降级本地嵌入式（30s 超时），不影响业务 |
| 智谱 API 返回 401 "令牌已过期或验证不正确" | 每周赠送 token 有有效期，过期需重新领取 |
| 想用 DeepSeek 同时做对话与 RAG 嵌入 | DeepSeek **无 embedding API**（`POST /embeddings` 实测 404），嵌入需另配智谱 `embedding-3` 或本地模型，见 §7 P0-1 |
| LLM 调用失败导致业务失败 | 约定：所有 LLM 依赖必须可降级（参考 `_compose_reply` 的模板回退），见 §5 硬约定 #11 |
| winget 报 0x8a15000f | 源损坏，放弃 winget，改官网/镜像直接下载 |
| 高风险单据提交后没人能审（任务停在「处理中」） | 审批链解析不出审批人——多半是部门没设主管、或该业务类型没配规则。查 `GET /admin/departments`（主管是否为空）与 `GET /admin/approval-rules`；开发环境跑 `PYTHONPATH=. .venv/Scripts/python.exe scripts/seed_org_demo.py` 补齐演示组织 |
| 员工提交报销后待审批列表里找不到 | 确认提交人确实归属该部门（`users.department_id`），且其部门主管是你登录的账号；`seed_org_demo` 后 emp999 的报销才会路由到 admin001 |
| 集成用例报 `Event loop is closed` | pytest-asyncio 每个用例新建事件循环，全局引擎的连接池会绑定到已关闭的循环；集成用例需在用例结束 dispose 引擎（`test_approval_routing_integration.py` 里的 autouse fixture 已处理，新写集成用例照抄） |
| 直接在测试里 `db.add()` 用户与部门报外键违规 | SQLAlchemy 一次 flush 内的插入顺序不完全可控；分步 `await db.flush()`（先用户、再部门、再引用两者的行） |
| E2E 报 403「无权访问该会话」 | 会话状态在 Redis 里带属主（TTL 24h），沿用固定 conversation_id 会与上一轮的属主冲突（如上一轮由 admin001 建、这轮换 emp999）；E2E 已改为每次生成唯一会话 ID |
| 改坏了文件想回退，结果丢了未提交的新代码 | `git checkout -- <file>` 会连同未提交的改动一起回退。边写边提交（或先 `git stash`）——有前科：一次回退把本轮新增的 2 个用例一起丢了 |
| 单据提交后无人可审（任务停在「处理中」） | 见 §7 审批链解析失败的三条常见原因：部门没设主管、该业务没配规则、角色类审批人（role:hr / role:legal）没有在职成员 |
| 查余额说「年假剩余 0 天」却还能继续请年假 | **假期余额双口径**：状态查询取 HR，规则引擎校验用硬编码 `DEFAULT_LEAVE_BALANCE`，两者不一致。属已知问题，需先定口径再改（见 §7「新发现」） |
| 12 个工具全报 `'property' object is not callable` | 给 `ToolResult` 加实例属性时**不能叫 `text`**——会静默覆盖同名 classmethod `ToolResult.text()`（构造器）。已改名为 `text_content`，并有回归用例锁住；同类陷阱：任何与既有 classmethod 同名的实例属性 |
| 单据详情里审批状态显示成「待处理」或英文 `approve` | `approvals.status` 与 `tasks.status` 是两套取值，不能共用标签表。审批侧用 `status_query.approval_status_label()`（待审/已通过/已驳回/已处理/已跳过） |
| 用户拿着回复里的「受理编号 MOCK-xxxx」查不到单据 | 受理编号由 `ToolResult.external_id` 解析并由 `/chat/send` 落到 `tasks.external_id`；若下游响应不是 `{code,message,data:{external_id}}` 信封则解析为空（任务 `external_id` 仍为空，表现为按编号查不到）——对接真实下游时先确认字段名 |
| 状态查询/意图类回答永远是「正在为您查询…」这种占位话术 | 编排器返回的 `needs_*` 标记没有消费方。历史前科：`policy_query` 的 `needs_rag` 与 `status_query` 的 `needs_status_query` 都曾长期无人消费；新增此类标记时**必须同时接上消费方**，否则用户永远看到占位文案 |
| 改完后端行为没变 | 后端是**手动启停**且未开 `--reload`，改代码后需按 §2 重启进程（`netstat -ano \| grep :8000` 取 PID → `MSYS_NO_PATHCONV=1 taskkill /PID <pid> /F` → 重新 uvicorn）；注意 taskkill 的开关在 Git Bash 里要配 `MSYS_NO_PATHCONV=1` 且用单斜杠 `/PID` |

### ⚠️ 新发现（Batch 15 实测暴露，需决策后再动）

- **假期余额双口径不一致**：状态查询报的余额来自 HR 系统（开发桩返回年假 5 天），而规则引擎校验请假时
  用的是 `core/rules/engine.py` 里**硬编码的** `DEFAULT_LEAVE_BALANCE`（年假 10 天）。
  实测表现：查余额显示「年假剩余 0 天（已用 12 天）」，但同一账号仍能继续提交 2 天年假申请并被接受。
  两条口径都对不上，用户会认为系统在骗人。
  **根因**：P2-10「规则引擎配置化」未做——规则引擎从不读 HR。
  **为何没顺手改**：让规则引擎改读 HR 会**改变审批/校验的拦截行为**（超 HR 余额的申请将从「接受」变为
  「拒绝」），属业务语义变更，需产品/行政拍板口径（以 HR 为准？以本地额度为准？还是双读校验）。
  在此之前，状态查询的回复已**如实标注数据来源**，不把默认值当权威数据。
  另注：重复跑 E2E 会在同一账号上累积多张请假单，故「已用 12 天 > 额度 5 天」在开发库是正常现象。
