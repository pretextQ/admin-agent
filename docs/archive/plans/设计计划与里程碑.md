## 一、项目总体计划

### 1.1 项目周期

| 阶段 | 时间 | 主要目标 |
|------|------|----------|
| 阶段一：MVP | 第 1-4 周 | 跑通最小可用版本，验证技术可行性 |
| 阶段二：核心功能 | 第 5-10 周 | 完成高频场景，上线内部测试 |
| 阶段三：完整版 | 第 11-16 周 | 完成全部场景，正式上线 |
| 阶段四：优化迭代 | 第 17 周+ | 持续优化，扩展场景 |

### 1.2 里程碑定义

| 里程碑 | 时间点 | 交付物 | 验收标准 |
|--------|--------|--------|----------|
| M1：技术验证 | 第 2 周末 | 可运行的 FastAPI 骨架 + LLM 调用 demo | 能通过 API 发送消息并获得 LLM 回复 |
| M2：MVP 版本 | 第 4 周末 | 制度问答 + 会议室预定 | 能回答制度问题、能预定会议室 |
| M3：核心场景 | 第 8 周末 | 请假 + 报销 + 物资领用 | 端到端完成请假/报销流程 |
| M4：内部测试 | 第 10 周末 | 完整系统 + 测试报告 | 意图识别准确率 ≥ 92%（对齐 PRD 7.1），端到端完成率 ≥ 85%，转人工率 ≤ 20% |
| M5：正式上线 | 第 16 周末 | 生产环境部署 | 通过全部验收指标 |

> 意图识别准确率分阶段推进：第 2 周 ≥ 85%，M4/上线 ≥ 92%；其余验收指标见[需求文档](../../product/需求说明.md) 7.1。

### 1.3 阶段与演进路线映射

[需求文档](../../product/需求说明.md)第 8 节的演进路线按「月」划分，本计划按「周」拆分，两者映射如下：

| PRD 演进路线 | 对应设计计划阶段 | 时间 | 覆盖场景 | 差异说明 |
|--------------|------------------|------|----------|----------|
| 阶段一：标准高频场景（0-3 个月） | 阶段一 MVP + 阶段二前段 | 第 1-8 周 | 制度问答、会议室/车辆预定、综合查询、请假 | **请假明确归入核心功能阶段（第 7-8 周）**，与需求文档第 8 节已对齐 |
| 阶段二：复杂流程场景（3-6 个月） | 阶段二 + 阶段三前段 | 第 5-16 周 | 报销、差旅、物资领用、证明开具 | 报销/物资在核心功能阶段，差旅/证明在完整版阶段 |
| 阶段三：跨系统智能编排（6 个月+） | 阶段三末 + 阶段四 | 第 11 周+ | 入离职、用印/合同、固定资产、智能决策 | 用印/固定资产在完整版阶段，智能决策在优化迭代阶段 |

结论（消除阶段一歧义）：

- MVP（第 1-4 周）只交付制度问答、会议室预定、基础多轮对话与会话管理，不含请假。
- **请假属于核心功能阶段**，计划在第 7-8 周交付；综合查询/状态跟踪随审批流与审计在核心功能阶段一并落地。
- 需求文档第 8 节已按本映射对齐：阶段一不含请假，请假归入阶段二。

### 1.4 代码与目录约定

计划中所有代码与目录统一为以下布局（详见 [开发规范.md](../../guides/开发规范.md) 与 [代码风格指南.md](../../guides/代码风格指南.md)）：

| 层级 | 路径 | 说明 |
|------|------|------|
| 应用入口 | `app/admin_ai/main.py` | FastAPI 应用与生命周期 |
| 配置 | `app/admin_ai/config.py` | `Settings` + `get_config()` 单例 |
| 路由 | `app/admin_ai/api/` | v1 路由与 websocket |
| 核心 | `app/admin_ai/core/{agent,rag,tools,rules,auth}/` | 智能体、RAG、工具、规则、鉴权 |
| 数据 | `app/admin_ai/db/{database.py,models.py,schemas.py,orm/}` | ORM / Pydantic / 仓储 |
| 服务 | `app/admin_ai/services/` | 业务服务 |
| 中间件 | `app/admin_ai/middleware/` | 审计、限流、日志 |
| 工具 | `app/admin_ai/utils/` | 通用工具 |
| 迁移 | `migrations/` + `alembic.ini` | Alembic 迁移 |
| 测试 | `tests/conftest.py` + `tests/admin_ai/{test_api,test_core,test_services}` | 测试 |

- 导入统一为 `from app.admin_ai.xxx import yyy`，first-party 为 `app`。
- 软件版本统一为 `0.1.0`（`APP_VERSION`、FastAPI `version`、`.env`）。

## 八、环境分层（dev / staging / prod）

| 维度 | dev | staging | prod |
|------|-----|---------|------|
| 用途 | 本地/联调开发 | 验收与压测 | 生产 |
| 数据 | 造数据，禁止真实个人信息 | 脱敏数据，接近生产量级 | 生产数据 |
| LLM | 可用轻量模型或桩 | 与生产同模型 | 生产模型，私有化/混合部署 |
| 配置 | `DEBUG=true`，宽松 CORS | 与生产一致 | `DEBUG=false`，白名单 CORS |
| 部署 | 本地 docker-compose | 独立命名空间 | 多副本 + Nginx，灰度发布 |
| 密钥 | `.env` 本地 | 独立密钥 | 密钥管理服务，定期轮换 |
| 访问 | 开发者 | 项目组 + 干系人 | 全员 |
| 发布 | 自由 | 每次候选版本 | 经上线检查清单与审批 |

- 三套环境变量命名一致，仅取值不同；禁止在 dev/staging 复用生产密钥。
- staging 与 prod 保持同配置形态，用于上线前最终验证与压测。

## 十、回滚预案

### 10.1 触发条件

- 出现 P0/P1 缺陷且 30 分钟内无法修复
- 关键路径错误率 > 1%，或首响应持续 10 分钟 > 3s
- 数据一致性异常（对账不平）

### 10.2 回滚动作

| 层面 | 动作 | 说明 |
|------|------|------|
| 应用 | 切回上一个稳定镜像 tag | 保留最近 3 个版本，支持一键回滚 |
| 数据库 | 执行 `alembic downgrade` 到上一版本 | 破坏性变更新增列/双写/兼容期，禁止直接 drop |
| 配置 | 恢复上一版本配置 | 通过 feature flag 关闭新功能 |
| 知识库 | 恢复索引快照 | 按 embedding 版本回退 |
| 流量 | Nginx 摘除异常副本 | 多副本逐步切换 |

### 10.3 回滚后处理

- 核对数据一致性，补齐回滚期间产生的单据
- 通知干系人，24 小时内提交复盘报告与改进项
